## 1. Goal

Upgrade `data/sts1/` — which already holds a complete wiki-sourced dataset (371 cards, 193 relics, 42 potions, 62 monsters with per-ascension moves, 52 events, Neow, achievements, score; browsable in `review/index.html`) — into a **first-hand, schema-validated, machine-executable** dataset extracted from `desktop-1.0.jar`, so the web remake can import it and run combat without hand-coding each card.

**The existing data is the baseline, not waste.** It is kept in git history and used in three ways: (a) `tools/diff-baseline.ts` compares every extracted number/name against the wiki-era record and writes `data/sts1/_baseline-diff.json`, so each discrepancy is reviewed (the code wins, but the list tells us where the wiki was wrong and where an extractor may be wrong); (b) hand-written fields with no code equivalent — monster `pattern` prose, `notes`, event flavour summaries — are carried over into the new records; (c) the current `enemies.json` move tables serve as the first golden-value set for the monster extractor.

Success criteria (all must hold):

1. Every StS1 entity class in the jar has exactly one record in `data/sts1/` (counts asserted by tests).
2. Every numeric field (cost, damage, block, magic, HP, move damage, relic counters) is extracted from the decompiled class, never typed by hand, and carries a `source.class` pointer.
3. Every card, relic, power and potion has an `effects`/`triggers` DSL entry, or an explicit `custom` marker. `custom` coverage is reported in `TODO.md`.
4. `npm test` passes: schemas, cross-references, counts, golden values, text/number consistency.
5. `review/index.html` renders the new fields; `review/data.js` is produced by a Node script (Python removed).
6. `TODO.md` lists remaining work and exact resume commands.

## 4. Pipeline

```
desktop-1.0.jar ─┬─ unzip localization/{eng,zhs}/*.json ──┐
                 └─ CFR → decompiled/sts1/**/*.java ───────┤
                                                           ▼
                                      tools/extract/*.ts  → data/sts1/*.json (+ _unresolved.json)
                                                           │
            data/sts1/*.effects.json (curated by agents) ──┤
                                                           ▼
                                      tools/validate.ts   → fail loudly, or
                                      tools/merge.ts      → packages/sts-data/dist/*.json + types
                                      tools/build-review.ts → review/data.js
                                      tools/status.ts     → TODO.md Status block
```

npm scripts: `decompile`, `extract`, `validate`, `merge`, `build:review`, `status`, `test`, and `all` (= extract → validate → merge → build:review → status).

Rules:

- Extraction is deterministic and idempotent. Re-running never touches `*.effects.json`.
- Anything a parser cannot resolve is written to `_unresolved.json` with class path + source line. It is never silently defaulted. The test suite requires the file to be empty.
- Each extractor prints `found/expected` counts against the class listing of the jar.
- Provenance on every record: `source: { class, jar: "desktop-1.0", jarSha256 }`.

## 5. Data model

### 5.1 Card

```jsonc
{
  "id": "Bash",
  "name": { "en": "Bash", "zh": "痛击" },
  "description": { "en": "Deal !D! damage. NL Apply !M! #yVulnerable.", "zh": "造成 !D! 点伤害。 NL 给予 !M! 层 易伤 。" },
  "upgradeDescription": { "en": null, "zh": null },
  "color": "red", "type": "attack", "rarity": "basic", "target": "enemy",
  "cost": 2,
  "base":    { "damage": 8,  "block": null, "magic": 2 },
  "upgrade": { "cost": null, "damage": 2, "block": null, "magic": 1 },
  "keywords": [],
  "upgradeKeywords": null,
  "playable": true,
  "obtainable": true,
  "effects": [
    { "op": "damage",     "target": "enemy", "amount": "damage" },
    { "op": "applyPower", "target": "enemy", "power": "Vulnerable", "amount": "magic" }
  ],
  "upgradeEffects": null,
  "source": { "class": "com.megacrit.cardcrawl.cards.red.Bash", "jar": "desktop-1.0", "jarSha256": "<hex>" }
}
```

- Enums: `color` ∈ red|green|blue|purple|colorless|curse|status; `type` ∈ attack|skill|power|status|curse; `rarity` ∈ basic|common|uncommon|rare|special|curse; `target` ∈ enemy|allEnemies|self|none|selfAndEnemy|all.
- Files: `cards/red.json green.json blue.json purple.json colorless.json curse.json status.json special.json`. `special.json` holds the jar's `tempCards` and `optionCards` (e.g. Shiv, Smite, Insight, the Discovery/Attack-Potion option cards). Their `color` keeps the game's real `CardColor` (mostly colorless/purple); the file itself is the grouping, and an extracted boolean `obtainable` (false for temp/option cards and for cards the game excludes from pools) replaces any hand-typed marker. `playable` stays `true` unless the class sets `cost = -2`.
- `cost` is an integer, `-1` for X-cost, `-2` for unplayable (the game's convention).
- `keywords` ∈ exhaust|ethereal|innate|retain|unplayable|selfRetain; derived from constructor flags.
- Placeholders `!D! !B! !M!` and `NL` are kept verbatim; the engine substitutes at render time.
- `upgrade` holds **deltas** parsed from `upgrade()`: `upgradeDamage(n)`, `upgradeBlock(n)`, `upgradeMagicNumber(n)`; `upgradeBaseCost(n)` is absolute and stored as `upgrade.cost: n`.
- **Upgrade semantics (fixed):**
  - `upgradeKeywords`: `null` means "same as `keywords`"; otherwise the **full** keyword array after upgrade (e.g. Body Slam+ drops `exhaust` → `[]`). Extracted from flag assignments inside `upgrade()`.
  - `upgradeEffects`: `null` means "same ops as `effects`, with `amount` references resolving to upgraded numbers" (covers ~90 % of cards). Otherwise it is the **full replacement** op list for the upgraded card (not a patch). Curated.
  - Both fields are part of the card schema; `upgradeEffects` items are validated against `dsl.schema.json`.
- `source` is the same object on every entity: `{ class, jar, jarSha256 }`.

### 5.2 Effect DSL (`schemas/dsl.schema.json`)

A flat list of ops. Vocabulary is a closed enum:

| op | required fields | notes |
|---|---|---|
| `damage` | target, amount | single hit; `repeat` for multi-hit |
| `damageAll` | amount | all enemies |
| `block` | amount | self |
| `applyPower` | target, power, amount | `power` must exist in powers.json |
| `draw` | amount | |
| `discard` | amount, `choose` (bool) | |
| `exhaust` | amount, `choose` / `from` (hand\|drawPile\|discardPile) | |
| `gainEnergy` | amount | |
| `heal` / `loseHp` | target, amount | |
| `addCard` | card, count, to (hand\|drawPile\|discardPile\|exhaust), upgraded | `card` must exist |
| `channelOrb` / `evokeOrb` | orb / count | Defect |
| `enterStance` | stance | Watcher |
| `scry` | amount | |
| `removeDebuffs` | target | |
| `upgradeCards` | from, count | |
| `shuffle`, `playTopCard`, `setCost`, `doubleBlock`, `doubleStrength` | per op | |
| `custom` | id, note | escape hatch; engine implements by `id` |

Common optional fields on any op:

- `amount` ∈ integer \| reference. References are resolved by the host entity at run time:
  | reference | valid in | resolves to |
  |---|---|---|
  | `"damage"` `"block"` `"magic"` | cards | the card's current (possibly upgraded) base values after power/relic modifiers |
  | `"x"` | cards | energy spent on an X-cost card |
  | `"energy"` | cards, relics | player's current energy |
  | `"potency"` | potions | `potency.base`, adjusted per ascension and doubled by Sacred Bark when `sacredBarkDoubles` |
  | `"stacks"` | powers | the power's current stack amount |
  | `"counter"` | relics | the relic's current counter value |
  The schema enforces the "valid in" column per entity file.
- `target` ∈ self\|enemy\|allEnemies\|randomEnemy\|none.
- `repeat` (integer or amount-ref).
- `if` ∈ a **closed** condition enum, finalized in `dsl.schema.json` before curation starts. Initial list: `targetHasPower:<Power>`, `selfHasPower:<Power>`, `handEmpty`, `handAllAttacks`, `inStance:<Stance>`, `lastCardType:<Type>`, `hpBelowHalf`, `targetIntent:attack`, `drawPileEmpty`, `firstCardThisTurn`.

**Vocabulary governance.** Finalizing `dsl.schema.json` (ops, condition enum, per-op required fields) is the first task of the implementation plan. The schema carries `"$comment": "dsl v1"`; adding an op or condition during curation bumps the minor version, and `npm run validate` re-validates all earlier batches, so there is never a batch written against an older vocabulary.

Target: ≤ 10 % of cards use `custom`. The current count is printed by `npm run status`.

| Entity | Extracted fields | Curated |
|---|---|---|
| Relic | id, name{en,zh}, flavor, description (joined `DESCRIPTIONS`, `#b` counter substituted), tier (starter\|common\|uncommon\|rare\|boss\|shop\|event\|special\|blight), pool (red\|green\|blue\|purple\|shared — **from `RelicLibrary.initialize()`'s `addRed/addGreen/addBlue/addPurple/addShared` calls, not the relic class**), counterStart, landingSound ignored, source | `triggers: [{ on: <hook>, do: [ops] }]` with hooks combatStart\|turnStart\|turnEnd\|cardPlayed\|attackPlayed\|onRest\|onPickup\|onShuffle\|onExhaust\|onVictory\|onChestOpen\|atDamageGive\|atDamageReceive\|modifyBlock\|custom |
| Power | id, name, description, type (buff\|debuff), turnBased, canStack, priority, source | `triggers` (same hook set + `atEndOfRound`, `onApply`, `onRemove`) |
| Potion | id, name, description, rarity (common\|uncommon\|rare), targetRequired, potency{base, perAscension}, sacredBarkDoubles, source | `effects` |
| Monster | id, name, act, tier (normal\|elite\|boss), `hp: Asc<{min,max}>`, moves[{ byte, name, intent, `damage: Asc<int>`, `hits: Asc<int>`, `block: Asc<int>`, powers[{ power, `amount: Asc<int>` }] }], source. **`Asc<T>` = `{ base: T, asc?: [{ level: int, value: T }] }`**, where `level` is the `ascensionLevel >= N` threshold found in the class (normal monsters use 2/7/17, elites 3/8/18, bosses 4/9/19; the structure does not hardcode these) | `pattern` prose carried over from the current data. **Move selection (`getMove`) is deliberately not modelled as data**: in the jar it is branchy code with roll thresholds and `lastMove`/`lastTwoMoves` history checks (verified on `JawWorm`, `GremlinNob`, `TheCollector`); it will be ported as one small TypeScript function per monster in sub-project 2, reading its numbers from this record |
| Encounter | act, kind (weak\|normal\|elite\|boss), monsters[], weight — sourced from `MonsterHelper.getEncounter` and the `Exordium` / `TheCity` / `TheBeyond` `generateWeakEnemies` / `generateStrongEnemies` / `generateElites` / `initializeBoss` lists | none |
| Event | id, name, act/pool, text (eng/zhs `events.json`: DESCRIPTIONS + OPTIONS strings), source | `options[{ text, requirement, outcomes[] }]` in `events.effects.json` — event classes are irregular state machines, so option structure is **curated**, not parsed; outcomes DSL ops: gold, hp, maxHp, card, relic, potion, curse, combat, custom |
| Neow | the four blessing stages with options and drawbacks | none |
| Keyword | id, names[], description{en,zh} | none |
| Character | id, startHp, startGold, startingDeck[], startingRelic, orbSlots, cardColor | none |
| Map | grid size, path count, room weights, forced rows (treasure 9, rest 15), boss pools per act, shop prices | none |

### 5.4 Schemas

`schemas/*.schema.json`, draft 2020-12, `additionalProperties: false` everywhere. **Schemas describe the in-memory join** (extracted record + its `effects`/`triggers` from the sibling `*.effects.json`), which is exactly the shape shown in §5.1 and the shape `merge.ts` writes to `dist/`; `validate.ts` performs that join itself before validating, so it can run before `merge`. The two source files are additionally checked by lightweight structural rules (extracted file: no `effects` key; effects file: object keyed by id, every key must exist in the extracted file). `tools/validate.ts` uses Ajv and additionally checks cross-references: every `power` in `applyPower` and in monster `moves[].powers[].power`, every `card` in `addCard`, every `monsters[]` entry in encounters, every `startingRelic` and `startingDeck[]` id, exists.

## 6. Workflow

The implementation plan is split in two phases so the repetitive curation work is gated on a finished, tested pipeline:

- **Phase A — pipeline:** toolchain, `decompile`, `class-filter`, all extractors, schemas incl. the finalized `dsl.schema.json`, `validate`, `merge`, `build-review` (with StS2 bundling preserved), the adapted StS1 review view, tests 1–6, `TODO.md`. Ends with every entity extracted and `effects` empty everywhere.
- **Phase B — curation:** the DSL batches of §6.2, each a small commit, with `status` updating `TODO.md` after each batch.

### 6.1 Extraction (automated)

Regexes anchored on the game's regular idioms:

- `super(ID, cardStrings.NAME, "img", <cost>, cardStrings.DESCRIPTION, CardType.X, CardColor.Y, CardRarity.Z, CardTarget.W)`
- `this.baseDamage = N; this.baseBlock = N; this.magicNumber = this.baseMagicNumber = N;`
- `upgradeDamage(N) upgradeBlock(N) upgradeMagicNumber(N) upgradeBaseCost(N)`
- `this.exhaust = true; this.isEthereal = true; this.isInnate = true; this.selfRetain = true;`
- Monsters: `setHp(min, max)`, `AbstractDungeon.ascensionLevel >= N` branches, `setMove((byte)n, Intent.ATTACK, damage, hits, isMulti)`, `DamageInfo(this, N)`.
- Relics: `super(ID, "img", RelicTier.X, LandingSound.Y)`, `this.counter`.

If a file matches none of the expected shapes, the record is emitted with the fields that were found and an `_unresolved.json` entry.

### 6.2 Curation (agent-driven batches)

- Batch size ≈ 25 entities. Inputs: decompiled `.java` for the batch, `dsl.schema.json`, two worked examples. Output: one `*.effects.json` chunk and a note per `custom`.
- Order: Ironclad → Silent → Defect → Watcher → colorless/curses/status → relics → powers → potions → events.
- Acceptance per batch: `npm run validate` passes, and a reviewer agent re-derives 20 % of the entries (random sample) from the Java source and confirms them. Any numeric mismatch rejects the batch.

### 6.3 Testing (Vitest, `npm test`)

1. Schema validation of every data file.
2. Cross-reference integrity.
3. Count assertions. Expected counts are **derived** from the jar class listing filtered by `tools/extract/class-filter.ts` (excludes abstract/helper classes such as `AbstractCard`, `AbstractRelic`, `AbstractPower`, `PotionSlot`, `MonsterGroup`, `EnemyMoveInfo`, `CardGroup`, inner classes `$`, and the `deprecated` subpackages; includes monster/event subpackages `exordium|city|beyond|ending|shrines`). The literal numbers 371 playable cards, 180 relics + 13 blights, 42 potions, 62 monsters, 52 events are kept as a **single sanity assertion**; if the derived count disagrees with a literal, the test names both so the discrepancy is investigated rather than fought.
4. Golden values (~30), covering all three monster tiers: Bash 8/2 → 10/3; Strike 6 → 9; Defend 5 → 8; Jaw Worm HP 40–44 (A7 42–46), Chomp 11 (A2 12); Gremlin Nob (elite) HP 82–86 (A8 85–90); The Guardian (boss) HP 240 (A9 250); Anchor 10 block; Burning Blood heal 6; Fire Potion 20 damage; Cultist Ritual 3 (A2 4, A17 5).
5. Text/number consistency: substituting `!D!/!B!/!M!` in the `eng` description with `base.*` must reproduce the wiki-known numbers for the sample set; and descriptions that mention `!M!` require `base.magic != null`, etc.
6. `_unresolved.json` is empty.
7. DSL coverage report (not a failure, written to `TODO.md`).

### 6.4 Review UI

`review/index.html` is kept, and its **StS1 view is adapted** to the new data shape (this is a rework of the StS1 entity tabs, not a cosmetic addition). The page currently shares one `ENTITIES` column configuration across both games; it becomes **per-game column definitions** (StS1 reads `name.zh`/`description.zh`/`base`/`upgrade`, StS2 keeps its flat fields). Entity keys change (`enemies` → `monsters`, `cards_neutral_groups` → per-color files, hash routes `#db/sts1/<entity>` updated), Chinese prose fields are replaced by `name.zh` / `description.zh`, and the following are added: base/upgrade numbers column, DSL rendered as a bullet list, `source.class` in the expanded row, en/zh toggle, validation banner read from `review/validation.json` (written by `tools/validate.ts`).

`tools/build-review.ts` replaces `review/build.py` and **must keep bundling `data/sts2/` unchanged** into `window.GAME_DATA.sts2` (porting `flatten_neow`, the envelope unwrapping and the neutral-card grouping logic as they apply to StS2), so the StS2 tab keeps working. `review/architecture.html` added (this document, visual).

## 7. Error handling

- Extractors exit non-zero and list offenders when a pattern is unexpected.
- `validate` blocks `merge`, `build:review`, and `status`.
- Curation reviewer rejects a batch on any numeric disagreement with the Java source.
- `custom` is allowed but counted; the count is visible in `TODO.md` and the review page.

## 8. Risks

| Risk | Mitigation |
|---|---|
| CFR output varies by class (inlined constants, ternaries for ascension) | `java-parse.ts` normalizes; unresolved cases are explicit, not guessed |
| DSL too small for odd cards | `custom` escape hatch, tracked; vocabulary can grow in a later minor version |
| Chinese text mismatches between `zhs` keys and class IDs | Keys are the same string IDs in all languages in StS1; test asserts every `eng` key has a `zhs` key |
| Copyright | No art/audio/text redistributed beyond mechanics and localization strings already public on wikis; assets stay local and ignored |
| Scope creep into the engine | Monster AI, VFX, and asset loading are explicitly deferred |

## 9. Engine findings carried forward to sub-project 2

Recorded here because they were verified while checking feasibility against the decompiled core (41 classes read: `GameActionManager`, `DamageInfo`, `AbstractMonster`, `MapGenerator`, `random/Random`, `AbstractDungeon`, `ShopScreen`, `RelicLibrary`, `CardLibrary`, `MonsterHelper`, …). They constrain the game spec, not this data spec, but the data layer must not make them harder:

1. **Action queue is the engine.** All game logic funnels through one ordered action list with `addToTop`/`addToBottom`, a `cardQueue`, and a `WAITING_ON_USER`/`EXECUTING_ACTIONS` phase machine. Visual actions (`VFXAction`, `SFXAction`, `WaitAction`, `ShakeScreenAction`) are interleaved; the web engine emits them as UI events and keeps the simulation deterministic.
2. **Damage formula**: base → owner `atDamageGive` → stance → target `atDamageReceive` → owner `atDamageFinalGive` → target `atDamageFinalReceive` → `floor`, clamp ≥ 0, computed in Java `float`. The TS engine uses `Math.fround` at each step to round identically.
3. **RNG fidelity**: `RandomXS128` (xorshift128+) with a per-stream call counter; separate streams (`aiRng`, `cardRandomRng`, `mapRng`, `monsterRng`, `relicRng`, `potionRng`, `treasureRng`, `eventRng`, `merchantRng`, `shuffleRng`, `cardRng`, `miscRng`) seeded from the run seed. Porting it exactly gives a test oracle: the same seed must yield the same Act 1 map and Neow options as the real game.
4. **Map generation** (`MapGenerator`, ~250 lines) is a pure algorithm and ports directly; its constants go in `map.json`.
5. **God objects** `AbstractDungeon` (2,680 lines), `AbstractCard` (2,566), `AbstractPlayer` (2,218) mix state, rendering and input; they are re-partitioned, never ported line-by-line.
6. **Monster AI** is code, not data (see §5.3); ported per monster in TS.
