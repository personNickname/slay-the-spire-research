0总览：这个游戏到底是怎么"转"的

先给结论，再给逐条证据。每个 蓝色标签 都是反编译源码的 文件:行号，鼠标悬停看完整路径。
为什么现在的引擎"像一坨"：原版是 动作队列 + 钩子 架构——卡牌、能力、遗物、怪物几乎从不直接改状态，只往队列里塞 Action；回合阶段不是一个函数，而是 getNextAction() 按固定优先级轮询 4 个队列"自然流出来"的。现有 TS 引擎是把结果手写成一条直线流程（endTurn() 里逐个怪物 tick 毒→行动→仪式…），所以每加一个机制就要在多处补特判，顺序永远对不上。

八条核心规则

  1. 一切皆 Action。card.use()、power.atStartOfTurn()、monster.takeTurn() 只做一件事：addToBot/addToTop(new XxxAction)。真正改血量、格挡、牌堆的代码只在 Action.update() 和 Creature 的少数方法里。
  2. 顺序 = 入队位置。addToBot 排队尾，addToTop 插队头（下一个执行）。同一方法里连续 addToTop(A); addToTop(B) 的执行顺序是 B→A。
  3. 回合阶段由队列优先级驱动。actions → preTurnActions → cardQueue → 怪物入队 → monsterQueue → 新回合。只有上一级为空才轮到下一级。
  4. 钩子在固定位置、按固定对象顺序触发。例如打出一张牌：玩家能力 → 所有怪物的能力 → 遗物 → 姿态 → 荒疫 → 手牌 → 弃牌堆 → 抽牌堆。
  5. 伤害算两遍。先算"面板值"（力量/虚弱/易伤/姿态 → info.output），到结算时再在 creature.damage() 里扣格挡并跑受击钩子。HP_LOSS 类型跳过格挡。
  6. 能力有三个不同的"回合节拍"。atStartOfTurn（持有者回合开始：中毒）、atEndOfTurn（持有者回合结束：金属化、玩家仪式）、atEndOfRound（所有怪物行动完之后：虚弱/易伤/脆弱 −1、怪物仪式）。
  7. 13 条独立 RNG 流。其中 5 条每层用 seed + floorNum 重置；牌库洗牌、怪物 AI、卡牌奖励互不干扰。
  8. 怪物意图是"上回合末"掷出来的。takeTurn() 的最后一个动作是 RollMoveAction，用 aiRng.random(99) 调 getMove(num)。

一个完整回合的时间线（从点"结束回合"到下一次可以出牌）

  1. A. 玩家回合结束
  2. 点击结束回合 → 往 cardQueue 放一个 card == null 的哨兵项；endTurnQueued = true。
  3. 取到哨兵 → callEndOfTurnActions()：遗物 onPlayerEndTurn → 玩家能力 atEndOfTurnPreEndTurnCards(true) → 入队 TriggerEndOfTurnOrbsAction → 手牌 triggerOnEndOfTurnForPlayingCard（灼伤/腐朽/悔恨等把自己排进 cardQueue 自动打出）→ 姿态 onEndOfTurn。
  4. 队列和 cardQueue 都排空后 isEndingTurn = true → room.endTurn()：立刻跑玩家能力 atEndOfTurn(true)，然后入队 清空出牌队列 → DiscardAtEndOfTurnAction → (EndTurnAction, Wait, MonsterStartTurnAction)。
  5. DiscardAtEndOfTurnAction：保留牌移入 limbo → 其余手牌弃掉（符文金字塔/均衡除外）→ 保留牌回手（触发 onRetained）；虚无牌此时 triggerOnEndOfPlayerTurn 消耗。
  6. EndTurnAction → turnHasEnded = true。
  7. B. 怪物回合
  8. MonsterStartTurnAction → monsters.applyPreTurnLogic()：每只存活怪物先失去格挡（壁垒除外）再跑能力 atStartOfTurn —— 所有怪物的中毒在任何怪物行动之前统一入队结算。
  9. 队列空 → monsters.queueMonsters() 把存活怪物放进 monsterQueue。
  10. 逐只出队：m.takeTurn()（把本回合招式的动作全部入队，最后一个是 RollMoveAction）→ m.applyTurnPowers()（duringTurn）。它入队的动作会在下一只怪物出队前全部执行完。
  11. C. 回合交替（同一个函数里同步完成）
  12. monsters.applyEndOfTurnPowers()：每只怪物的能力 atEndOfTurnPreEndTurnCards(false) + atEndOfTurn(false) → 玩家能力 atEndOfRound → 每只怪物能力 atEndOfRound。
  13. 玩家回合开始钩子：姿态 atStartOfTurn → 遗物 atTurnStart → 手牌 atTurnStartPreDraw → 三个牌堆 atTurnStart → 玩家能力 atStartOfTurn（玩家中毒在这里入队）→ 充能球 onStartOfTurn。
  14. ++turn；turnHasEnded = false；玩家失去格挡（壁垒/残影不失去；外卡钳只失去 15）。
  15. 入队 DrawCardAction(gameHandSize, endTurnDraw=true) —— 构造这个动作的瞬间就回复能量（energy.recharge()）并触发 onEnergyRecharge；然后遗物 atTurnStartPostDraw、能力 atStartOfTurnPostDraw（都只是入队）。
  16. 队列按入队顺序执行：步骤 10–11 里钩子塞的动作 → 抽牌 → PostDraw 动作 → 启用结束回合按钮。此后队列空 = 等待玩家。
直接后果举例（对应你之前指出的 bug）：① 怪物的毒在"怪物回合开始"统一结算，不是逐只、更不是挂毒时；② 虚弱/易伤是 atEndOfRound 才 −1，且怪物施加的首回合不减（justApplied）；③ 怪物仪式是 atEndOfRound 加力量且首轮跳过，玩家仪式是 atEndOfTurn ；④ 怪物的格挡在它自己回合开始时才清空，所以能挡住玩家整个回合。

3GameActionManager：四个队列与主循环

整个战斗引擎的心脏，490 行。

Action 自己的基类只有三样东西：isDone、duration 计时、shouldCancelAction()（目标已死或来源已死则取消）。全部 277 个 Action 子类及其调用的核心变更方法见 ③ 页（筛选"动作 Action"）。

4战斗开始：从进房间到第一回合

三步：建怪 → preBattlePrep → 第一回合钩子。注意第一回合和后续回合走的不是同一段代码。
由入队顺序推出的实际执行顺序：Wait → 怪物战前动作 → 遗物 atPreBattle 的动作 →（第一回合帧）回能 → atBattleStartPreDraw 的动作 → 抽 5 张 → atBattleStart 的动作（所以"准备背包"的额外 2 张在起手 5 张之后抽）→ atTurnStart 的动作 → …
第一回合与后续回合的差异：没有 atTurnStartPreDraw、没有能力的 atStartOfTurnPostDraw、不清格挡、不触发 atEndOfRound；回能走的是 GainEnergyAndEnableControlsAction 而不是 energy.recharge()。

5出牌流程

拖牌 → cardQueue → 校验 → onPlayCard 钩子 → useCard → UseCardAction（构造时 onUseCard，执行时归位）。
打出"痛击"时队列的真实样子：use() 入队 [伤害, 施加易伤] → new UseCardAction 构造时各 onUseCard 钩子把自己的动作 addToBot → 最后 UseCardAction 自己入队。即 [伤害, 易伤, 钩子动作…, UseCardAction]。而 onPlayCard 钩子的动作排在 卡牌效果之前。两类钩子一前一后，这是很多遗物/能力时序的根源。

6伤害管线

面板计算（三个入口）→ DamageAction → creature.damage()（玩家版和怪物版钩子顺序不同）。全程 float 运算，最后 MathUtils.floor。

玩家受伤：AbstractPlayer.damage(info)

怪物受伤：AbstractMonster.damage(info)

玩家版 vs 怪物版的差别（都要照抄）：怪物没有 onLoseHp / onLoseHpLast / onInflictDamage；怪物的 wasHPLost 在 onAttack 之前且不要求伤害 > 0；怪物的 onAttacked 不受 owner == null 影响。34 个怪物子类还重写了 damage()（觉醒者、黑暗体等半死机制）——见 ② 怪物 damage。

7格挡与能力施加

关于"负面能力"的判定：力量 / 敏捷 / 集中 在 updateDescription() 里按 amount 正负把 type 切成 BUFF 或 DEBUFF ，所以 −N 力量同样会被人工制品挡掉。新引擎里 type 是 Power 实例的字段，不再维护"负面 ID 白名单"。
回合结束弃牌的细节：循环里每个 DiscardAction 的 amount 都是整手牌数，所以第一个就把手牌弃光，其余空转——照抄即可，不要"优化"。

钩子矩阵：每个钩子在哪里被触发、谁实现了它

机器扫描全部源码得到。"调用点"回答什么时刻触发（哪个类的哪个方法、第几行调用了这个钩子），"实现者"回答谁会响应。重写时每个钩子按这张表逐行核对：调用点要在新引擎的同一位置，实现者要一个不漏。

调用点颜色：精确 接收者类型已确定 · 父类型 接收者声明为父类（如 AbstractCreature.damage），运行时可能分派到这里 · 推断 接收者类型靠全局同名字段/返回值推断

类行为索引：每个类的每个方法做了什么

对每个逻辑类的每个方法提取"行为指纹"：入队了哪些 Action（队头/队尾）、new 了哪些 Power、用了哪条 RNG、直接调用了哪些核心改状态方法。这是重写阶段的移植清单——一个类移植完，它的指纹必须与这里一致。画面/音效/本地化类不计入；指纹为空的类（没有入队、没有 new 能力、不用 RNG、不调核心方法，例如纯数值修正的能力）不在本页列出，它们的钩子实现在 ② 页。

指纹是正则扫描的结果，不是执行轨迹：它列出方法体里出现过的入队与调用，不区分 if 分支、不保证先后顺序，间接调用（经辅助方法入队）也看不到。它用来保证"不漏"，精确顺序仍以 ① 页的逐行追溯和源码为准。
图例：T:Xxx addToTop 入队 · B:Xxx addToBot 入队 · S:/?: 其它入队方式 · [XxxPower] 构造的能力 · {rng} 使用的随机流 · Type.method 直接调用的核心方法 · 灰色小字 = 该类重写的钩子

对照对象：packages/sts-engine/src（12 个文件）。下表只列结构性差距——它们是之前那些具体 bug（毒的时机、仪式、虚弱不影响意图、格挡被无视）的共同根源。

#原版（反编译）现有 TS 引擎后果
1所有效果经 GameActionManager 的队列执行；回合阶段由 getNextAction() 轮询 4 个队列产生 combat.ts 里有一个闭包队列 addToBot/addToTop/flushActions，但整个引擎只有 4 处调用；绝大多数效果是立即执行的函数调用"先入队后结算"的顺序全部丢失：连击中途死亡、受击反馈、抽牌触发等的先后与原版不同

3能力是对象，行为写在自己的钩子里（161 个子类，47 个钩子）；引擎只负责在固定位置遍历 powers 调钩子能力是 {id, amount}，行为散落在 endTurn / startPlayerTurn / dealDamage / applyDamagePowers 里的 if (hasPower("X"))；减益用 tickDebuffs 统一递减没有 atEndOfRound / justApplied / priority 这些概念，新增能力只能再加特判
4遗物同样是钩子对象（190 个子类，61 个钩子），与能力在同一批调用点、按固定先后被遍历relicEffects.ts 用自定义事件名 fireRelics(run, "atTurnStart")，调用位置是手工安排的（例如 atBattleStart 在第一回合抽牌之后才触发）遗物与能力的相对顺序、遗物触发时刻与原版不一致

可以保留的部分：rng.ts（位级实现已对齐 RandomXS128）、数据抽取管线（tools/，卡牌/遗物/怪物的静态数值）、地图生成的算法骨架（重写时按 §13 逐行复核）。其余战斗相关代码按下面的方案整体替换，而不是继续打补丁。

重写方案

原则

  1. 一个 Java 类对应一个 TS 类，类名、方法名、钩子名原样保留。例如 PoisonPower.atStartOfTurn()、Cultist.takeTurn()、ApplyPowerAction.update()。review 时可以把 TS 文件和反编译文件并排逐行比对。
  2. 每个方法头部标注来源 // AbstractPlayer.java:1369-1498。
  3. 引擎核心不认识任何具体的牌/能力/遗物/怪物，只负责：队列调度、在固定位置遍历钩子。出现 if (id === "某能力") 的地方必须是原版也这样写的地方（如 hasPower("Barricade")）。
  4. 去掉时间，保留顺序。原版 Action 靠 duration 分帧；新引擎里每个 Action 只保留"第一帧逻辑"和"结束帧逻辑"两个时点，纯等待/特效/音效 Action 变成空操作，但仍然入队（保证其它动作的相对位置不变）。
